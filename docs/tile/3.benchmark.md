# Benchmark methodology

This document explains how to run the per-operator microbenchmarks and
interpret the results.

## Running

```bash
conda activate base
which nvcc
export CUDA_HOME=/home/ubuntu/miniconda3
export PATH=/home/ubuntu/miniconda3/bin:$PATH
export LD_LIBRARY_PATH=/home/ubuntu/miniconda3/lib

# All operators, both backends.
python -m tests.bench_all

# Just TileLang.
python -m tests.bench_all --backend tilelang

# Just the reference (triton / torch.compile).
python -m tests.bench_all --backend triton

# Single op.
python -m tests.bench_rmsnorm --backend both --warmup 10 --iters 100
```

The CLI flags are consistent across all `bench_*.py` scripts:

- `--backend {triton,tilelang,both}` — which backend(s) to time.
- `--warmup N` — number of untimed calls before timing (default 10).
- `--iters N` — number of timed calls (default 100).

## How it's measured

Each `bench_*.py` uses `torch.cuda.Event` for GPU-side timing:

```python
s = torch.cuda.Event(enable_timing=True)
e = torch.cuda.Event(enable_timing=True)
s.record()
fn(*args)
e.record()
e.synchronize()
times.append(s.elapsed_time(e))
```

The reported number is the **median** of `iters` samples. Median is
robust to occasional CUDA-driver stalls.

## Apples-to-apples rules

- Both backends run on the same shapes (`M`, `num_heads`, `head_dim`,
  `dtype`).
- Both backends run with the same `warmup` and `iters`.
- Both backends run on the same GPU, single-process, no other work.
- We do not reset `torch.cuda.empty_cache` between backends — the
  cache is a perf win and identical for both.

**Headlines**:

- RMSNorm / SiluAndMul / RoPE: TileLang is **1.4x–2x faster** at every shape.
- store_kvcache: TileLang is **20x slower** because the kernel is tiny
  (microseconds) and the TileLang launch overhead dominates. For this
  op, the triton kernel remains the better choice at small N.

## Interpreting the results

- **Speedup ≥ 1.05x**: TileLang is winning meaningfully. Worth
  keeping in the TileLang backend.
- **Speedup 0.95–1.05**: noise. TileLang is roughly equivalent.
  Worth keeping only if you expect easy future wins (e.g. Hopper
  warp-specialization).
- **Speedup < 0.95**: TileLang is losing. Either revert the op to
  the reference backend, or spend time on autotuning.
- **Compile time**: TileLang's first call is *very* slow (seconds).
  The latencies above are after `warmup`, so they reflect steady-
  state performance. If you need warm-cache timings, run with
  `--warmup 50 --iters 200`.

## Notes on TileLang overhead

The launch overhead for a TileLang-compiled kernel is non-trivial
on small workloads (`< 100us`). For ops that at runtime are
dominated by launch overhead (super-short kernels like store_kvcache),
the win is on the *theoretical* autotuned body, not on the *measured*
end-to-end. For long-running kernels where the body amortizes the
launch cost (RMSNorm, SiluAndMul, attention), the gain is real.
